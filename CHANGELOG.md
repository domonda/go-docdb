# Changelog

All notable changes to `github.com/domonda/go-docdb` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [v1.1.0] - 2026-08-24

### Fixed
- **Concurrent `storeconn.AddDocumentVersion` calls no longer silently lose one of the updates.** `AddDocumentVersion` reads the latest version, carries its file set forward, applies its own changes and inserts. Two callers doing that at once both read the same latest version and both build their result from it, so whichever inserts second writes a file set that never saw the first one's changes — the first writer's version stays in the list, but every version after it is missing its files. Nothing about the second insert looked wrong on its own: its version timestamp is unique and it is not a genesis, so neither existing constraint stopped it. `localfsdb` serializes writers per document with a mutex; `storeconn` has no equivalent and cannot have one, because its writers are separate processes sharing Postgres and S3. The chain itself is now the constraint: a document's versions are a chain, so a version has at most one successor, which the new unique index `document_version_one_successor_per_version_idx` on `(document_id, prev_version)` enforces. The writer that loses gets `docdb.ErrDocumentChanged` — the optimistic concurrency conflict the type was declared for and never used — and can redo its work from the new latest version. **Deploying this needs a migration check:** the index cannot be created while any document has two versions naming the same `prev_version`, and such rows can exist both from updates already lost this way and from the middle-version restore fixed below. Query for them before creating the index.
- **`storeconn.RestoreDocument`'s rollback no longer deletes file content it did not write.** It recorded the content hashes it uploaded and undid them with `DeleteDocumentHashes`, which matches on the hash alone — but a hash does not identify one object. A `DocumentStore` keys a file by name *and* hash, so a document holding the same bytes under two names holds two objects, and a restore that uploads `b.txt` with the content of an already-stored `a.txt` recorded a hash that both share. A later failure then deleted both, corrupting a version the restore was never touching. The rollback now records the files it wrote as name/hash pairs and deletes exactly those. Two more shapes of the same defect are fixed with it: a version whose metadata this call created but whose files the `DocumentStore` already held was rolled back through the composite `DeleteDocumentVersion`, whose cleanup deleted the content hashes that version alone referenced — content this call never wrote — so the rollback now removes the metadata row through the `MetadataStore` and leaves every object it did not upload; and a failed metadata delete no longer lets the file cleanup run, because a version that is still committed while its content is gone is worse than an orphaned object, which the presence check of the next restore finds and a content-addressed write of the same bytes overwrites.
- `storeconn.AddDocumentVersion` uploads the bytes it hashed. It read every written file to derive its size and content hash and then handed the same `fs.FileReader`s to the `DocumentStore`, which read them a second time to upload. A `FileReader` is not required to return the same bytes twice — an `fs.File` whose backing file is rewritten between the two reads is enough — and the version then recorded the hash of one read while the store held the other. Files are addressed by content hash, so that object can never be found again under the recorded hash and every later `ReadHashedDocument` of the document fails, silently, until a backup or migration trips over it. The bytes read for the hash are now the bytes written.
- An additive `RestoreDocument` fills in a run of consecutive deleted versions instead of failing on it. A restored middle version takes back the successor `DeleteDocumentVersion` relinked onto its predecessor, and the successor it named was the backup's immediate next version — which is not on the destination yet when two adjacent versions are missing. Nothing was relinked, and the insert then collided with the version that does chain off the predecessor: restoring `v1` into a destination holding `v0` and `v3` of `v0→v1→v2→v3` named the absent `v2`, left `v3` on `v0`, and was refused as `ErrDocumentChanged`. The successor is now the first version of the backup the destination actually holds, which keeps the guarantee that only a version of the backup may ever move — a version the destination has and the backup does not is still never named.
- `HashedDocument.Validate` rejects a per-version `CompanyID` that is set but malformed. `uu.IDNil` means the version inherits the document's company and stays valid, but any other value is persisted by both restore implementations as committed history, and `localfsdb` files the document under a directory named after it, which the company enumeration then cannot parse.
- Restoring a deleted middle version no longer leaves the version after it pointing at the wrong predecessor. `DeleteDocumentVersion` relinks a deleted version's successor to the deleted version's own predecessor, so removing v1 from v0→v1→v2 leaves v0→v2. Restoring v1 then inserted it with v0 as its predecessor and left v2 there too, so both named v0: the chain forked, and v2 claimed to follow a version that is no longer the one before it. `CreateDocumentVersion` now hands that successor over, relinking it onto the restored version, but only the one version named by the new `CreateDocumentVersionInput.RelinkSuccessor` — which only `RestoreDocument` sets, to the backup's own next version. The successor has to be named rather than found, because no property of the stored rows identifies it, and two rows that a search would have matched must not move. A concurrent append names the same predecessor, and which of two writers inserts first is not decided by their version timestamps, because a `CreateVersionFunc` stamps its version when it starts: a slower writer that started earlier inserts a version sorting *before* one already chained off the same predecessor, so adopting whatever sorts after the new version would hand a loser the winner's version, dropping the winner's change from every version after it — the very update loss the index above exists to refuse. A version that exists only on the destination of a merge-restore and is absent from the backup can chain off the same predecessor too, and `RestoreDocument` documents that such versions are kept as-is; relinking one would leave it naming a predecessor whose file set it never derived from. An append names no successor, relinks nothing, and gets `ErrDocumentChanged` whichever timestamp it holds. Naming a version that is not stored, or that no longer chains off the predecessor, relinks nothing and is not an error — a restore inserts oldest first, so every version but the last names a successor that is still to come.
- `storeconn.RestoreDocument` writes only the file content the `DocumentStore` does not already hold, instead of every file of every version it touches. The presence of each candidate file is already established per file to decide what to skip; reducing that to one bool per version and discarding the rest meant a version missing a single object had all of its files re-uploaded to repair it. Files are addressed by name and content hash, so a file carried forward unchanged is one object however many versions reference it, and it is now written once: a restore of a document with V versions of F files where each version changes one file uploads F+(V-1) objects rather than V×F. Nothing is written for a version whose content all turned out to be present.
- `pgstore.CreateDocumentVersion` inserts inside a savepoint when the caller is already in a transaction, so the duplicate the resume path above provokes no longer takes the caller's transaction down with it. `ErrVersionAlreadyExists` and `ErrDocumentAlreadyExists` are answers this method is expected to give, not just failures — `RestoreDocument` asks for a version it knows is stored in order to write the file content that is missing under it, and continues past the rejection. But both come from a unique violation, and a violation raised directly in the caller's transaction aborts all of it: every statement after it, the rest of the restore and whatever else the caller is doing, fails with `current transaction is aborted, commands ignored until end of transaction block` (SQLSTATE 25P02), while the restore itself still returned nil. Reporting success on a dead transaction is the same silent-data-loss shape the resume fix exists to remove, and it was invisible to the existing tests because the in-memory `MetadataStore` fake covering the inserting mode has no transaction semantics at all. Rolling back to a savepoint contains the violation to the insert that caused it; `TestSyncDocument_ResumesInterruptedCopyWithoutVersionsExistMode` covers the resume against real Postgres inside a caller's transaction. Not reached in versions-exist mode, which verifies instead of inserting, and unchanged for a caller that is not already in a transaction: the insert then gets its own transaction as before.
- `pgstore.CreateDocumentVersion` reports a relink that collides with an existing successor as `docdb.ErrDocumentChanged` rather than as a raw unique violation. The `RelinkSuccessor` update moves the named version onto the one being inserted, and that can violate the one-successor-per-version index itself when some row already chains off the new version — which a partially applied restore or a hand-repaired chain leaves behind. The violation was returned unwrapped, so the caller got a Postgres index name and no way to tell a conflict it may retry from the new latest version apart from a failure it must not.
- `pgstore.CreateDocumentVersion` no longer decides what a rejected insert means from which unique index Postgres happened to name. A row that duplicates an already-stored version violates both `(document_id, version)` and `(document_id, prev_version)`, and Postgres reports whichever index it checks first — an order nothing in the code or the schema pins, and that a `REINDEX` or a dump/restore can change. It currently names the timestamp constraint, which mapped to `ErrVersionAlreadyExists` and let a resumed restore continue past its own expected duplicate; had it named the successor index, every such resume would have failed instead with `ErrDocumentChanged`. The version is now looked up once the savepoint is rolled back and the transaction can be queried again: stored means this insert duplicates it, absent means another writer appended after the same predecessor. Not covered by a test — the failure needs the two indexes created in the opposite order, which cannot be arranged without DDL against the shared test table.
- `storeconn.RestoreDocument` with `recreate=false` no longer reports success for a document whose file content it never copied. It decided what to skip from two unrelated sources: whether *any* object exists under the document (`DocumentStore.DocumentExists`) and the version list of the `MetadataStore`. That is only sound when both stores are populated together. Copying into a `DocumentStore` while reusing a `MetadataStore` that already holds every version of the document — the migration case `pgstore.ContextWithMetadataStoreVersionsExist` exists for — is exactly the opposite: the version list is complete before anything is copied, so once an interrupted run (Ctrl-C, network error, crash) had written a single object, the document counted as existing, every version counted as already restored, `RestoreDocument` returned nil, and the caller counted the document as fully synced while its later versions were never written. Silent data loss at cutover. A version is now skipped only when the `MetadataStore` holds it **and** the `DocumentStore` holds every one of its files; a version whose metadata exists but whose files do not gets its files written, and the duplicate metadata insert that a non-verifying `MetadataStore` rejects for it is expected rather than fatal. Such a version is not added to the rollback set, because this call did not create it. The presence of every candidate file is checked in a single `DocumentStore` call per document, so a fully present document is still skipped without a per-version or per-file round trip storm. What the `MetadataStore` holds is queried whether or not the `DocumentStore` reports the document as existing, so a copy interrupted before its first write resumes too instead of pushing the already-stored versions through the genesis create path, which a `MetadataStore` that really inserts refuses as a duplicate; the company-mismatch check is correspondingly gated on the `MetadataStore` knowing the document rather than on blobs existing. A version whose stored metadata is not the backup's is no longer accepted silently: because the rejected insert stored nothing, the already-stored version's file set is compared against the backup's before any content is written under it. A restore that fails after creating the document's genesis version but with the `MetadataStore` already holding other versions now rolls that one version back individually instead of deleting the whole document's metadata, which would have taken rows this call never created. `docdb.SyncDocument`'s documentation described the old skip-by-version-presence behaviour and is corrected.
- `storeconn.RestoreDocument` with `recreate=true` repairs a document that exists as metadata alone instead of failing on it. The up-front delete was gated on `DocumentExists`, which reports only what the `DocumentStore` holds, so it was skipped for a document whose version rows were mirrored before any file content was copied — the state a migration into a shared `MetadataStore` starts from, and what a write cancelled between the two stores leaves behind. The loop then took the genesis path for a version the `MetadataStore` already held, which the one-genesis-per-document index refuses as `ErrDocumentAlreadyExists`, and `CreateDocument`'s rollback deliberately keeps the blobs it wrote for that error, because under concurrency they belong to the winner: the call failed on exactly the half-written state `recreate` exists to repair, and left new orphaned content behind while doing so. It now deletes whatever either store holds. `storeconn.DeleteDocument` reporting not-found — which it does only when neither store holds anything — is not a failure for a restore that is about to write the document from scratch, and is ignored.
- Every `storeconn` rollback now runs on `context.WithoutCancel(ctx)` (`rollbackCtx`): `RestoreDocument`, `CreateDocument`, and `AddDocumentVersion`'s `rollbackNewVersion`. Cancellation is precisely the case that leaves a half-written document behind, and cleaning up with the same cancelled context made every delete fail, so the partial state survived — and was then misread by the skip logic above on the next run. The three rollbacks are structurally identical, so fixing only one left the other two producing exactly the metadata-without-file-content state the skip logic above had to be taught to detect: `AddDocumentVersion` cancelled during the blob write commits a metadata version, fails the write, then fails its own rollback. **This changes what a cancelled write leaves behind:** previously a call aborted by cancellation kept what it had created (plus the joined cleanup errors); now it is rolled back, as it already was for any other failure. A rollback keeps the context values, so it still runs against the same transaction and store configuration, and gets a fresh one-minute deadline of its own: generous, because giving up halfway through deleting a document's objects leaves exactly the partial state the rollback exists to remove, but finite, so a cancelled or timed-out caller — an HTTP handler, a shutting-down worker — is not held indefinitely.
- A panic from a store no longer escapes a `storeconn` write with the half-written document left behind. `CreateDocument`, `AddDocumentVersion` and `RestoreDocument` roll back what they created when they fail, but the rollback only runs when the call ends with an error, and a panic is not one — so a panicking `MetadataStore` or `DocumentStore` left a committed metadata version whose file content was never written, which is exactly the state the restore above has to detect and repair. All three now convert a panic into that error first, and `AddDocumentVersion` rolls back from a `defer` instead of at each failure site, so a panic between the metadata commit and the end of the call is undone like an error is. `CreateDocument` looked like it already did this, but its `errs.RecoverPanicAsErrorWithFuncParams` sat inside the rollback closure, where `recover` returns nil: it only recovers when the deferred function calls it itself. `localfsdb`'s `CreateDocument` and `AddDocumentVersion` had the same hole and are fixed the same way. A panic still reaches the caller — as an error carrying the panic value and its call stack, the way a panicking `CreateVersionFunc` or `OnNewVersionFunc` already did.
- `storeconn.DeleteDocument` deletes a document's file content even when the `MetadataStore` reports the document as not found, and only reports not-found when neither store holds anything. The two stores are written and deleted one after the other, so a failure or cancellation between the steps leaves file content without metadata — and returning the `MetadataStore`'s not-found before touching the `DocumentStore` orphaned that content permanently, because every later delete stopped at the same not-found. It also made such a document impossible to restore again: `RestoreDocument` with `recreate=true` deletes before rebuilding and failed on that same not-found.
- `pgstore.DeleteDocument` reports a document that is not there as `docdb.ErrDocumentNotFound` instead of a raw `sql.ErrNoRows`. It read the delete's `returning true`, which yields no row at all when nothing matches, so `QueryRowAs` failed with `sql.ErrNoRows` before the not-found branch below it could run — that branch was dead code. `storeconn.DeleteDocument` keys on `os.ErrNotExist`, which `ErrDocumentNotFound` matches and a bare `sql.ErrNoRows` does not, to go on and delete file content whose metadata is already gone: against Postgres it stopped at that error instead, so the orphaned-content fix above only ever worked against the in-memory fake, and `RestoreDocument` with `recreate=true` failed on the same error. The deleted rows are now counted inside a CTE, the way `DeleteDocumentVersion` already did it. The test covering this asserted only `sql.ErrNoRows`, which both the old and the new behaviour satisfy because `ErrDocumentNotFound` matches that too, and now asserts the documented error and `os.ErrNotExist`.
- `DirFileProvider` no longer reports hidden entries and sub-directories as files of a document version. A `.DS_Store` from a Finder visit, the temp file of an interrupted rsync, or an NFS silly-rename ends up in a version directory without ever being tracked in the version info — and `ReadHashedDocument` then rejects the whole document with "exists in storage but is not tracked in version info", failing every reader of that document and aborting a bulk operation over an entire company at that document. `localfsdb` already skipped hidden entries when enumerating company and version directories, but the file listing of a version did not, and it also reported sub-directories as files. `ListFiles` now skips both, and `HasFile` and `ReadFile` apply the same filter, so a filename either belongs to the provider or does not, no matter which method is asked. The filter lives in the helper rather than in `localfsdb.DocumentVersionFileProvider` so that it also covers the previous-version provider handed to a `CreateVersionFunc` and the listing `localfsdb` builds a version's metadata from. Note that this filters the helper for every consumer, including the ones that point it at a directory which is not a document version. This is a behavior change for a consumer that deliberately stored a dot-file in a version directory: that file is now invisible through the provider. Untracked files are still rejected — nothing here adopts them into a version.
- `localfsdb` builds a new version's `VersionInfo` through `DirFileProvider` instead of a raw directory listing, so writing a version's metadata skips the same entries as reading its files back. An untracked hidden file in the previous version's directory was otherwise recorded in the new version's `RemovedFiles`, claiming the removal of a file that had never been added.
- `localfsdb.CreateDocument` rejects a document whose files are all hidden instead of creating one that tracks nothing. It checks that it was passed at least one file, because a document cannot start with an empty, change-less version — but that check is on what the caller passed, and the version's file list is built by enumerating the written directory through `DirFileProvider`, which does not report hidden entries as files of a version. Passing only hidden files therefore produced exactly the version the check exists to reject: created without an error, tracking no files, and reading back empty through every reader of the document, including `ReadHashedDocument` and the backups taken from it. The check is now on the resulting file set, as it already was in `AddDocumentVersion`. A document mixing hidden files with tracked ones is still created, with the hidden ones untracked as before.
- `localfsdb.RestoreDocument` rejects a version whose files are all hidden, as `CreateDocument` and `AddDocumentVersion` already did. It is the path most likely to be handed one: the filenames come from a backup taken elsewhere, and `storeconn` addresses files by name and content hash, so it stores a dot-prefixed name like any other. Restoring such a version wrote the file, recorded a version tracking nothing and reported success — a document that `HashedDocument.Validate` and therefore every later backup, sync and restore rejects. The check now lives in `newVersionInfo`, where a version's file set is established by enumerating the written directory through `DirFileProvider`, so all three paths get it from one place instead of two of them repeating it and the third not having it.
- **A document moved between companies no longer loses the move when it is backed up, synced or restored.** A document is moved by committing a new version that names the new company (`CreateVersionResult.NewCompanyID`), so the versions committed before the move keep naming the previous one and the move stays readable in the document's history. `HashedDocument` carried a single `CompanyID`, read from `Conn.DocumentCompanyID`, and `HashedDocument.VersionInfo` stamped it onto every version, so a backup dropped the per-version company and a restore filed the whole document — including the versions from before the move — under its current company. That is a silent rewrite of history on every `SyncDocument`, and it also makes the restored metadata differ from what the source recorded: `VersionInfo.Equal` compares `CompanyID`, so a destination whose versions already exist (`pgstore.ContextWithMetadataStoreVersionsExist`, the migration case) rejects the first version of the first document that was ever moved and aborts the sync of the whole company. `HashedVersion.CompanyID` now carries the company of its own version, `ReadHashedDocument` fills it from each version's `VersionInfo`, and `localfsdb` and `storeconn` write each version with the company of that version. The exception is the latest version, which is read as owned by the company the `Conn` reports for the document: an implementation with a separate owner marker can have that marker name a company its latest version does not (`SetDocumentCompanyID` moves the marker without committing a version), while an implementation without such a marker derives the owner from the latest version — so the two would otherwise disagree about who owns the restored document. `Validate` enforces that invariant, and a version that leaves `CompanyID` unset inherits the document's, so a `HashedDocument` built by hand for a document that was never moved is unaffected.
- `localfsdb.AddDocumentVersion` no longer rejects a move that changes no file as `ErrNoChanges`. A move is a version that changes nothing but the company, and the change-less check compared only the file sets, so moving a document was only possible for a caller that happened to write a file in the same version — which is how it worked at all: the caller's own metadata file changed with the move. `ErrNoChanges` is now returned only when the files *and* the company are unchanged, so a move committed this way can be backed up and restored instead of being rejected as a change-less version.
- A document that was moved between companies is no longer listed under both of them by `pgstore`. `CompanyDocumentIDs` selected every version row naming the company and deduplicated by document, so a moved document was listed under its previous owner as well — where a bulk operation over that company (`SyncAllCompanyDocuments`, `CopyAllCompanyDocumentFiles`, a migration to another store) then processed a document it no longer owns, and wrote it into the wrong company on the destination. `CompanyIDs` reported the previous company as a company with documents for the same reason. Both now resolve a document to the company of its latest version only, which is what `DocumentCompanyID` already answered and what `localfsdb` — which keeps one marker directory per document and moves it — has always done. `CompanyIDs` does it as a `distinct company_id` candidate list plus an exists probe per candidate rather than by reducing the whole table to one row per document, because the reduction has to read and sort every version row of every document before it can answer — a full scan and sort of the table on every call, at an entry point that bulk operations and `routerconn`'s fan-out use.
- `localfsdb.DeleteDocumentVersion` re-assigns the document to the company of the version that becomes the latest one. A document belongs to the company of its latest version, so deleting the version that moved it left the document owned by, and listed under, a company that none of its remaining versions names. `pgstore` derives the owner from the latest row and needed no change; `localfsdb` keeps a separate company marker, which now follows the delete.
- `RestoreDocument` with `recreate=false` no longer refuses to restore a move. Both implementations compared the destination's current company against the backup's current company, so a backup whose newer versions moved the document — a destination synced before the move, which is the state every incremental sync of an active company runs into — failed with a company mismatch instead of copying the move. The comparison is now against the company the backup names for the latest version the destination actually has (`docdb.CheckRestoreCompanyID`), which still refuses a backup of another company's document under the same ID, and the destination follows the move once the newer versions are restored.
- **`HashedDocument.Validate` no longer rejects a version whose files and company are identical to its predecessor's, which used to make such a document impossible to back up, sync or migrate.** Creating one is still refused where versions are created — that check moved to being the only enforcement of the rule — but a *stored* document can hold one regardless, through operations documented to do exactly that: `DeleteDocumentVersion` removing the middle of `v0(F), v1(G), v2(F)` leaves two adjacent versions with the same files, and `SetDocumentCompanyID` rewrites the company of a pure move version to the one its predecessor already names, collapsing the two. `RestoreDocument` validates before touching anything, so the rejection did not undo the collapse — it only meant the document could never be copied again, and `SyncAllCompanyDocuments` failed on it for good. A backup has to be able to represent what a store actually holds. The two invariants `Validate` does enforce are unchanged: every version has at least one file, and the latest version names the document's current company.
- `localfsdb.DeleteDocumentVersion` no longer re-derives the document's company when the deleted version was not the latest one. Only removing the latest version changes which version the owner comes from; doing it on every delete overwrote a company marker that `SetDocumentCompanyID` had moved without committing a version — a marker that names a company no version names, on purpose — so deleting the *oldest* version of a moved document silently moved it back.
- `localfsdb.RestoreDocument` with `recreate=false` no longer re-derives the document's company when the merge did not write the version that is now the latest one. The re-derivation ran on every merge into an existing document, including one that wrote nothing at all, so every incremental sync into this store undid every `SetDocumentCompanyID` move — including a sync of the document into itself. It now runs only when this call wrote the document's new latest version, which is the only case in which the restore decided who owns it.
- `localfsdb.RestoreDocument` with `recreate=false` relinks the successor of a version it fills back into the middle of an existing chain, the same way `storeconn` does through `CreateDocumentVersionInput.RelinkSuccessor`. Restoring `v1` into a destination that has `v0` and `v2` left `v2` still chained off `v0`, so two versions named the same predecessor and `v2` named one that was no longer the version before it. Only the backup's own next version is relinked, and only while it still chains off the version's own predecessor, so a version the destination has and the backup does not is kept as-is.
- `storeconn.RestoreDocument` rolls back the file content it wrote for a version whose metadata was already stored. Such a version is not the call's to delete and never entered the rollback's version list, so a failure mid-restore left every object uploaded before it orphaned — the whole of a migration into a `MetadataStore` in versions-exist mode, where no version is ever inserted by the restore. The content hashes this call writes are now recorded before each write and deleted on failure. They are safe to delete because the presence check now covers the files of every version of the backup rather than only of the versions that can be skipped, so every file written is one the `DocumentStore` reported absent.
- `storeconn.AddDocumentVersion` records a written file's `Size` as the length of the content it hashed, instead of taking it from a separate `fs.FileReader.Size()` stat. The two need not see the same bytes — a file whose content changes between the read and the stat, or any `FileReader` whose `Size()` does not match what `ReadAll` returns — and a version stored with a `Size` contradicting its `Hash` fails every later `ReadHashedDocument` of it with a byte-count mismatch. `HashedDocument.VersionInfo` already recorded the same field this way.
- `routerconn` refuses a company change that would move a document to a company on another backend, rather than committing it on the backend the document is on. Both `SetDocumentCompanyID` and a version naming a `CreateVersionResult.NewCompanyID` route by document ID, so the document stayed put while `CompanyDocumentIDs` of its new company asked a backend that does not list it — and a company-wide sync or migration then skipped the document without reporting anything. Carrying a document over is a migration, not a company change, so the operation now fails and says so. The check for `AddDocumentVersion` wraps the `CreateVersionFunc`, because the new company is only known once that callback has run; returning the error from there rolls the version back atomically.
- `run_tests.sh` tears the compose services and their volumes down through an `EXIT` trap instead of only as its last line. `set -e` aborted the script at a failing `docker compose up --wait` or `init.sh`, and an interrupted run never reached the last line either, so the volumes stayed populated and the *next* run's `init.sh` died on the schema it found already there — a failure that outlived the run that caused it until someone ran `docker compose down -v` by hand.
- `pgstore`'s test fixtures honour every override map passed to a fixture constructor, not only the first. `Populator.DocumentVersion`, `DocumentVersionFile`, `createRecordIfNeeded` and `fillDataIntoStruct` each read `data[0]` on their own, so an override in a later map was neither applied nor rejected and the fixture was inserted with the generated default the caller had asked to replace. All of them now go through one merge, with a later map winning over an earlier one.

### Added
- `docdb.HashedVersion.CompanyID`, `HashedDocument.VersionCompanyID(VersionTime) uu.ID` and `docdb.CheckRestoreCompanyID(doc, destVersions, destCompanyID) error`: the per-version company of a backed-up document, its lookup with the inherit-from-the-document fallback, and the company check a `RestoreDocument` implementation applies before merging into an existing document. The check lives here rather than in each implementation because both compare the same two companies, and a divergence between two copies of it does not fail a test at build time but a migration halfway through a company's documents.
- New index `document_version_company_id_idx` on `docdb.document_version (company_id)`. `CompanyDocumentIDs` now checks whether the rows of the passed company are the latest version of their document, which starts from those rows; without the index that is a sequential scan of every version of every document. `CompanyIDs` uses it twice, for its candidate list and for each of its exists probes. The table had no index on `company_id` at all, so the previous listing was one too — this is a strict improvement, and the index can be created before or after deploying.
- `storeconn.DocumentStore.DocumentHashFilesExist(ctx, docID, files []docdb.FileInfo) (map[docdb.FileInfo]bool, error)`: reports for every passed file whether the store holds a file with that name and content hash, as a map keyed by the passed values (only `Name` and `Hash` are matched, never `Size`). A `DocumentStore` deliberately does not track versions — files are addressed by name and content hash — so this is how a caller determines whether a complete version is present: it is, exactly when all of its files are. The batch shape is what keeps the merge-restore check to one round trip for a whole document; `s3store` answers it from a single prefix listing rather than a `HeadObject` per file.
- `docdb.VersionInfo.SetFileDeltas(prevFiles map[string]FileInfo)`: derives `AddedFiles`, `ModifiedFiles`, and `RemovedFiles` by comparing `Files` against the complete file set of the previous version (pass `nil` for the first version of a document, which reports every file as added). The same diff was hand-written in four places — `HashedDocument.VersionInfo`, `localfsdb`'s `newVersionInfo`, `storeconn`'s `AddDocumentVersion`, and `storeconn`'s merge-restore — and their results are compared against each other: a `MetadataStore` in versions-exist mode verifies the `VersionInfo` a restore would insert against the stored one, so a divergence between two copies of the derivation does not fail a test at build time but a migration halfway through a company's documents. All of them now derive through `SetFileDeltas`, and `storeconn`'s merge-restore reaches it through `HashedDocument.VersionInfo`, which derives the whole `VersionInfo` a restored version is written from. It compares only filenames and content hashes, so a caller that knows just those of the previous version can build `prevFiles` without looking up file sizes; the lists are replaced rather than appended to, sorted by filename so they never depend on map iteration order, and left nil instead of empty.

### Changed
- **`storeconn.AddDocumentVersion` now returns `docdb.ErrNoChanges`** for a version that changes neither the files nor the company, which `docdb.Conn` documents as the answer of every implementation and `localfsdb` has always given. `storeconn` enforced nothing, so the two implementations disagreed on the one thing a versions-exist `MetadataStore` compares across them, and a change-less version committed on the S3 path produced a document that `HashedDocument.Validate` rejects — one that could never be backed up, synced or restored again. This is a behavior change for a caller that relied on a no-op version being committed on the S3 backend: it now gets the error it already got from `localfsdb`.
- **Breaking for `DocumentStore` implementers:** `DocumentHashFilesExist` and `DeleteDocumentHashFiles` are new methods on the `storeconn.DocumentStore` interface. Implementations outside this repository must add both; `s3store` is updated. No caller-facing API changed. `DeleteDocumentHashFiles(ctx, docID, files []docdb.FileInfo)` is the delete that mirrors `DocumentHashFilesExist`: it matches `Name` and `Hash` together and never `Size`, so a caller can undo exactly the files it wrote. `DeleteDocumentHashes` is unchanged and still deletes every file with a given hash whatever its name, which is what removing a version's content needs.
- **Relevant to `MetadataStore` implementers:** `storeconn.CreateDocumentVersionInput` has a new `RelinkSuccessor *docdb.VersionTime` field, and `MetadataStore.CreateDocumentVersion` documents what an implementation must do with it: when it is non-nil, relink that one version onto the new version if it still chains off `PreviousVersion`, and otherwise refuse a second version naming an already-used `PreviousVersion` as `docdb.ErrDocumentChanged`. An implementation must relink only the version named and must not search for one — neither by the version timestamps nor by any other property of the stored rows, because a concurrent append and a version absent from the backup being restored both chain off the same predecessor and can sort after the new version. A named version that is not stored relinks nothing and is not an error. Only `RestoreDocument` sets the field. Existing implementations keep compiling; one that relinks by search loses concurrent updates and mutates versions a merge-restore must keep as-is.
- `storeconn` merge-restore records its added/modified/removed lists sorted by filename instead of in map iteration order, a consequence of deriving them with `SetFileDeltas`. Version comparison is order-insensitive, so no two versions that compared equal before compare differently now; what changes is that the lists persisted for a restored version are deterministic.
- **`storeconn.AddDocumentVersion` records different change lists in two cases**, now that it derives them with `SetFileDeltas` from the resulting file set rather than classifying the files a `CreateVersionFunc` wrote by name. A file rewritten with byte-identical content is no longer recorded in `ModifiedFiles` — it changed nothing — and a `RemoveFiles` entry the previous version did not have is no longer recorded in `RemovedFiles`. `localfsdb` already behaved this way, so the two implementations disagreed on exactly the lists a versions-exist `MetadataStore` compares across them; `RemovedFiles` is now also sorted rather than in the order the `CreateVersionFunc` returned. A genuine content change is still a modification, and the resulting file set of a version is unchanged in every case.
- `run_tests.sh` runs `go test ./... -p 1` instead of a hand-maintained package list that omitted the root `docdb` package and `storeconn` — the two that hold most of the unit tests, so CI was green without ever running them. `-p 1` is required because the `s3store` and `integrationtests` packages share the one MinIO bucket and Postgres database of the compose services and each clears its bucket, so Go's default concurrent package execution makes them delete each other's objects. It also checks up front that `docker` and `psql` are installed and names the missing one instead of failing later with a cryptic error; both are preinstalled on GitHub-hosted Ubuntu runners.
- `pgfixtures.FixtureGlobalConn` and `s3fixtures.FixtureGlobalS3Client` fail the test when their backend is unreachable instead of skipping it, so a test suite that could not run its integration tests can no longer report success. Both fixtures skipped, which made a run with no Docker at all — and every partial variant of it — indistinguishable from a passing one: `go test` prints `ok` for a package whose tests all skipped and exits 0, so `run_tests.sh` and the GitHub Actions workflow that calls it were green whether the tests had verified anything or not. A `POSTGRES_PORT` that no longer matches the port mapping in `docker-compose.yml`, an edit to `.env.example`, or MinIO answering its `mc ready` healthcheck while rejecting the fixture credentials each produced exactly that, and each looked like a passing build. The skip existed so a bare `go test ./...` would work without Docker; that convenience is what silently removed most of the suite's coverage, and it is gone. Use `run_tests.sh`, which starts both services and waits for their healthchecks before running the tests; the failure message names it. **This is a behavior change for anyone running `go test` outside `run_tests.sh`:** the `pgstore`, `s3store`, and `integrationtests` packages now fail rather than skip when the compose services are not up.
- Every version the CI uses is pinned, so a build turns red because this repository changed rather than because something upstream did. The two workflows used `actions/checkout@v6`, `actions/setup-go@v6` and Go `1.26`, the security scan ran `securego/gosec@master`, and `docker-compose.yml` pulled `minio/minio:latest` — all of which resolve to whatever is newest at the moment the job starts, which is exactly what makes an unreproducible failure impossible to attribute and a green run on an old commit no longer meaningful. `@master` also means an arbitrary upstream commit runs inside CI with the job's token. The actions are pinned to exact release tags — `actions/checkout@v6.1.0`, `actions/setup-go@v6.5.0`, `securego/gosec@v2.28.0` — rather than to the moving major-version tags they used, Go is `1.26.5`, and the images are `minio/minio:RELEASE.2025-09-07T16-13-09Z` and `postgres:17.10`. Each pin was verified to name what the floating reference resolved to on 2026-08-07: `actions/checkout@v6` and `actions/setup-go@v6` point at the exact commits of `v6.1.0` and `v6.5.0`, and the two image digests are identical. The one thing that does change is the scanner gosec runs. Its action pins the scanner image by digest and bumps that digest on `master` after a release is cut, so the newest release tag lags one version behind: `securego/gosec@master` runs gosec 2.28.0, while `securego/gosec@v2.28.0` — the newest tag there is — runs 2.27.1. That is the trade this pin makes, one scanner version for a reference that cannot change under us, and it may report a different set of findings. `runs-on` stays `ubuntu-latest` deliberately: GitHub retires a pinned runner image on its own schedule, so pinning it trades a silent image upgrade for a hard failure on a date this repository does not control. Everything else now moves only by a commit that raises the pin.
- `VersionTime` and `VersionTime.Value` document that a version timestamp must only reach SQL as a `VersionTime`. Every conversion in this package truncates to milliseconds, but a PostgreSQL `timestamp(3)` column rounds: a version created at `15:04:52.3875` is truncated to `.387` and stored under that name in the file store, while inserting the untruncated `time.Time` rounds it to `.388` in the database. Nothing reconciles the two at read time, so the same version ends up with two identities one millisecond apart and the version lists of the two stores no longer match — which is what production `docdb.document_version` rows sitting exactly 1 ms after their file-store version are.

## [v1.0.1] - 2026-07-03

### Fixed
- `IdenticalDocumentVersionsOfDrivers` no longer reports two identical versions as different because of change-list ordering. It compared the drivers' `VersionInfo`s with `reflect.DeepEqual`, which compares the `AddedFiles`/`RemovedFiles`/`ModifiedFiles` slices positionally — yet those lists derive from non-deterministic map iteration, so identical versions whose lists happened to be in a different order were reported as different. `reflect.DeepEqual` also treated a nil slice/map as different from an empty one and compared version timestamps at nanosecond rather than the stored millisecond precision. It now uses `VersionInfo.Equal`, which compares the change-list sets order-insensitively and the timestamps at millisecond precision — the same comparison the Postgres versions-exist check already uses.

## [v1.0.0] - 2026-06-30

### Added
- `CompanyIDs(ctx) (uu.IDSlice, error)` on `docdb.Conn` and `storeconn.MetadataStore`, with a package-level `docdb.CompanyIDs` wrapper: returns the IDs of all companies that have documents, sorted by ID for a consistent order. `pgstore` selects `distinct company_id`; `localfsdb` lists the per-company sub-directories; `routerconn` fans out across all backends and deduplicates. Together with `CompanyDocumentIDs` this fully replaces the removed `EnumDocumentIDs` (iterate companies, then documents per company).
- `docdb.DocProgressCallback`: `func(ctx context.Context, docID uu.ID, index, total int)`, the progress callback type accepted by `SyncAllCompanyDocuments` and `CopyAllCompanyDocumentFiles`.

### Changed
- The callback-based `EnumCompanyDocumentIDs` is replaced by `CompanyDocumentIDs(ctx, companyID) (uu.IDSlice, error)`, which returns all of a company's document IDs as a slice sorted by ID for a consistent order, instead of invoking a per-document callback. This affects `docdb.Conn`, the package-level `docdb.EnumCompanyDocumentIDs` function (now `docdb.CompanyDocumentIDs`), `storeconn.MetadataStore`, and every implementation (`localfsdb`, `storeconn`/`pgstore`, `routerconn`, `MockConn`, `errConn`). The result is `nil` for a company with no documents. Unlike the previous unbounded enumeration this materializes the full ID slice, matching the existing usage which already buffered every ID before reading documents.
- `docdb.SyncAllCompanyDocuments` gains a trailing `onProgress docdb.DocProgressCallback` parameter. It fetches the document IDs via `srcConn.CompanyDocumentIDs`, then syncs them one after another. The known total lets `onProgress` (when not nil) be called before syncing each document with the document's zero-based index and the total to sync, letting callers log progress. Pass `nil` to keep the previous behavior. The `continueOnError` and `recreate` semantics and the returned `syncedDocIDs` are unchanged.
- `docdb.CopyAllCompanyDocumentFiles` gains a trailing `onProgress docdb.DocProgressCallback` parameter, mirroring `SyncAllCompanyDocuments`. It now collects the document IDs via `conn.CompanyDocumentIDs` up front and calls `onProgress` (when not nil) before copying each document with its zero-based index and the total count. Pass `nil` to keep the previous behavior.

### Removed
- `EnumDocumentIDs` is removed from `docdb.Conn`, the package-level `docdb.EnumDocumentIDs` wrapper, and `storeconn.DocumentStore` (and its `s3store` implementation). It enumerated every document across all companies via a callback; the new `CompanyIDs` + `CompanyDocumentIDs` slice methods cover the same need without a callback. No production code called it; the `routerconn` cross-backend fan-out and dedup it provided now lives in `CompanyIDs`.

## [v0.8.1] - 2026-06-29

### Fixed
- `s3store` no longer silently caps document operations at 1000 objects. `DeleteDocument`, `DeleteDocumentHashes`, and `DocumentHashFileProvider` each previously issued a single `ListObjectsV2` call — which AWS S3 limits to 1000 keys per response — so a document with more than 1000 stored objects had its extra files silently skipped: a delete would leave objects behind, and a hash lookup would miss files. All three now page through every object under the document prefix via the AWS SDK `ListObjectsV2` paginator, and deletes are split into batches of at most 1000 keys to stay within the `DeleteObjects` limit. `DeleteDocument` lists and deletes one page at a time, so memory stays bounded by a single page even for very large documents.
- `s3store` delete paths now surface the per-object failures S3 reports inside an otherwise-successful (HTTP 200) `DeleteObjects` response instead of ignoring them. S3 does not return these as a transport error, so a partial delete failure was previously swallowed and could leave objects behind without any error; the delete now fails loudly. The same check is applied to the test bucket teardown so a failed cleanup no longer surfaces later as a confusing `BucketNotEmpty`.

### Added
- `s3store.DeleteObjectsErr`: exported helper that converts the per-object `Errors` of an `awss3.DeleteObjectsOutput` into a Go error (and returns nil for a nil output or no failures), so callers performing their own `DeleteObjects` calls can detect the silent per-object failures S3 hides in a 200 response.
- `storeconn/README.md`: documents the split-store `Conn` — how `New` composes a `DocumentStore` and `MetadataStore`, how the content hash joins them, and how the orchestration layer keeps the two backends consistent (ordering and compensating rollback) without a distributed transaction.

### Changed
- `s3store.EnumDocumentIDs` is reimplemented on top of the AWS SDK `ListObjectsV2` paginator, replacing the hand-rolled continuation-token enumerator. Behavior is unchanged: every object in the bucket is scanned across all pages and each unique document ID is reported to the callback exactly once.
- Updated `aws-sdk-go-v2` (`service/s3` to v1.104.0, core to v1.42.0) and the remaining module dependencies to their current releases.

## [v0.8.0] - 2026-06-26

### Added
- `docdb.VersionInfo.Equal`: reports whether two `VersionInfo`s describe the same committed version — scalar metadata, the resolved file set (`EqualFiles`), and the added/removed/modified filename lists compared order-insensitively. The Postgres versions-exist check uses it, so a field added to `VersionInfo` is compared automatically instead of being missed by a hand-rolled field-by-field check.
- `ReadonlyConn`: wrap any `Conn` to hand out a read-only view. Read methods pass through to the wrapped connection; every write method (`SetDocumentCompanyID`, `CreateDocument`, `AddDocumentVersion`, `AddMultiDocumentVersion`, `DeleteDocument`, `DeleteDocumentVersion`, `RestoreDocument`) returns the new `ErrReadonly` sentinel without touching the underlying connection. Each write error names the document it refused, and `errors.Is(err, docdb.ErrReadonly)` matches.
- `pgstore.ContextWithMetadataStoreVersionsExist`: derives a context that switches the Postgres `MetadataStore` into versions-exist mode, treating it as immutable. `CreateDocumentVersion` inserts nothing and instead verifies the already-stored version is identical to what would have been inserted; `DeleteDocument` and `DeleteDocumentVersion` delete nothing and instead verify existence (`DeleteDocumentVersion` still reports the same left-over versions and blob hashes a real delete would, so the caller can clean up the `DocumentStore`). All three return an error if the version or document is missing, and `CreateDocumentVersion` additionally errors if any stored field differs from what it would have inserted. Intended for copying a document to a different `DocumentStore` while reusing a `MetadataStore` that already holds the versions (for example migrating only the file blobs to a new `DocumentStore`): the shared metadata is read and verified, never mutated, even on rollback.

### Changed
- Split-store API unification: `storeconn.MetadataStore`'s `CreateDocument` + `AddDocumentVersion` collapse into a single `CreateDocumentVersion(ctx, CreateDocumentVersionInput)`, and `DocumentStore.CreateDocument` is replaced by `CreateDocumentVersion(ctx, docID, version, files)`. The `CreateDocumentVersionInput.PreviousVersion` field is a `*VersionTime`: a nil value creates the first (genesis) version with `prev_version` stored as NULL, fixing a zero-`VersionTime` insert failure when adding a version that precedes a document's existing versions.
- `storeconn.DocumentStore.CreateDocumentVersion` now returns `[]*docdb.FileInfo` (name, size, content hash) for each stored file, in input order, alongside its error. The store already computes the content hash while writing each blob, so returning it lets the split-store genesis path (`CreateDocument`) reuse those `FileInfo`s instead of re-reading and re-hashing every file — halving file I/O and hashing on document creation.
- `storeconn.CreateDocumentVersionInput` gains an optional `Files` field holding the complete resolved file set of the new version. `AddDocumentVersion` and `RestoreDocument` already compute it, so they now pass it through and the Postgres `MetadataStore` uses it directly — skipping the extra `DocumentVersionInfo` query for the previous version and the redundant carry-forward + delta re-derivation on every appended/restored version. When `Files` is nil the store still derives the set from `PreviousVersion` plus the added/modified/removed lists.

### Fixed
- `storeconn` merge-restore (`RestoreDocument` with `recreate=false`) now stores `prev_version` as NULL for a restored version that precedes the document's existing versions, instead of passing a zero `VersionTime` and failing with "invalid zero VersionTime". This is the case the genesis-NULL change above was meant to cover; the split-store conn now actually passes a nil `previousVersion` for the earliest restored version.
- The split-store genesis path (`CreateDocument`) cleans up a failed create without orphaning blobs or destroying unrelated data. Because the up-front existence check proves the `DocumentStore` held no files for the document, the rollback deletes the whole document's blobs — which also removes objects left by a partial blob write that returned no `FileInfo`s — except when the metadata insert failed with `ErrDocumentAlreadyExists`. That error is exactly what disproves the existence check under concurrency: a concurrent `CreateDocument` (or a pre-existing metadata-without-blobs document being re-created) owns those content-addressed blobs, so deleting them would corrupt the winner; the identical objects are left in place instead. The metadata rollback deletes only the single version this call inserted (and only when it was inserted), targeting it with `DeleteDocumentVersion` rather than `DeleteDocument`, so a document that already holds versions in the `MetadataStore` (a fresh `DocumentStore` reusing a populated `MetadataStore`, or an inconsistent metadata-without-blobs state) is never wiped.
- The split-store `CreateDocument` now rolls back (and correctly reports) when its `onNewVersion` callback fails or the call panics. Inlining its helper had left it with an unnamed error return, so the deferred rollback and panic recovery silently saw a `nil` error: an `onNewVersion` failure left the genesis document committed, a recovered panic was reported as success, and rollback-cleanup errors were dropped. The error return is named again.
- `pgstore.MetadataStore.CreateDocumentVersion` maps a Postgres unique violation to `ErrDocumentAlreadyExists` for a genesis insert and `ErrVersionAlreadyExists` for an appended version, instead of leaking the raw driver error.
- The Postgres schema adds a partial unique index (`document_version_one_genesis_per_document_idx` on `(document_id) where prev_version is null`) enforcing at most one genesis version per document. This closes a gap where a document whose metadata existed but whose blobs were absent could be silently given a second genesis version with a different timestamp: the insert now raises a unique violation that `CreateDocumentVersion` maps to `ErrDocumentAlreadyExists`. Production schemas need the same index added by migration.
- `pgstore.MetadataStore.CreateDocumentVersion` now returns a not-found error when its non-nil `previousVersion` is missing from the `MetadataStore`, instead of silently dropping the carried-forward files (which would persist a version missing those files, or cause a confusing file-set mismatch in versions-exist mode).
- The split-store `CreateDocument` now refuses an already-existing document with `ErrDocumentAlreadyExists` (honoring the documented `Conn.CreateDocument` contract) before writing anything. Previously it proceeded, and on a later failure the genesis rollback could delete file blobs (deduplicated by content hash) and metadata shared with the pre-existing document. The existence check targets the `DocumentStore`, so copying into a fresh `DocumentStore` that reuses an already-populated `MetadataStore` (`ContextWithMetadataStoreVersionsExist`) is still allowed.
- The split-store genesis rollback no longer joins a spurious `ErrDocumentNotFound` onto the real failure cause when a `CreateDocument` fails before any metadata row is inserted (for example a blob-write error). The metadata rollback is skipped when nothing was inserted and the blob rollback ignores not-found, so `errors.Is(err, ErrDocumentNotFound)` (and the `os.ErrNotExist` / `sql.ErrNoRows` it matches) no longer reports a document that was never created.

### Removed
- `pgstore.NewReadOnlyMetadataStore` is removed. For an immutable Postgres `MetadataStore`, derive a context with `pgstore.ContextWithMetadataStoreVersionsExist` (versions-exist mode); for a fully read-only `Conn`, wrap one with `docdb.ReadonlyConn`.

- Bumped the Go toolchain to 1.26.

- `localfsdb.CreateDocument` is now race-safe under concurrent imports (go-fs bump), eliminating spurious "file already exists" errors when documents share UUID-prefix parent directories.
- `DeleteDocumentVersion` (Postgres) no longer deletes file blobs that sibling versions still reference, and no longer falsely raises `ErrDocumentNotFound` after a successful delete.
- `RestoreDocument` merge mode can now restore a deleted middle version instead of rejecting it.
- `ReadHashedDocument` now errors clearly when storage and version metadata disagree about a file, instead of reporting "expected 0 bytes" or silently skipping it.
- `localfsdb.RestoreDocument` writes the correct `VersionInfo` (predecessor and file diff) when restoring a version that precedes the document's existing versions; it previously diffed such a version against the latest on-disk version, corrupting its metadata.
- `localfsdb.AddDocumentVersion` runs its error-path cleanup while still holding the per-document lock, closing a window where a concurrent writer could chain a new version off a half-written one.
- `storeconn.AddDocumentVersion` rolls back the metadata version when the file-content write fails, and `storeconn.RestoreDocument` rolls back partially-restored versions on error, so a failed operation no longer leaves a version referencing missing file content.
- `localfsdb.RestoreDocument` (recreate mode) surfaces a company-ID read error instead of swallowing it, so it no longer silently leaves a stale company-document marker behind.
- `HashedDocument.VersionInfo` returns nil for an internally inconsistent document instead of panicking.

### Removed
